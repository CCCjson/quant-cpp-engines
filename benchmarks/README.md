# What actually decides fast and slow — an investigation that falsified its own premise

This is not a "C++ vs Python" scoreboard.

The investigation started from that premise, but **the first round of data falsified it**.
Everything after that is an attempt to answer: if it isn't the language, what is it?

Every conclusion rests on one dataset, one machine, and reproducible controlled experiments.
Every number can be traced to a file in [`results/`](results/) — this README is generated by
[`make_report.py`](make_report.py), nothing is copied by hand.

## The starting point: a sentence nobody had measured

This repository's design doc, [`docs/design-backtest.md`](../docs/design-backtest.md), contains
the line:

> **Performance**: the C++ per-bar loop is much faster than Python

An assumption from project kickoff that had **never been measured**. That kind of sentence is
the worst thing to carry into a technical conversation — the first question anyone competent
asks is "faster by how much."

Hence this investigation.

---

## The material: a genuine control group

The most common way to cheat at a performance comparison is to pit a carelessly written
implementation against a carefully tuned one. That was deliberately avoided here: the control
is not something written for this benchmark, it is **a Python backtest engine that actually ran
in production** and was retired wholesale once the C++ version matured. How it was recovered,
and the itemized list of changes made to it, are in [`ORIGIN.md`](ORIGIN.md).

Before any timing, a **hard gate**: on the same 180 real daily bars and the same strategy, the
two engines must agree item by item on the economic result. If they don't, they are not
computing the same thing, and timing them against each other is meaningless.

| Metric | Python | C++ | Diff |
|---|---|---|---|
| Final equity | 1,448,492.33183950 | 1,448,492.33183950 | 0.00e+00 |
| Total return | 0.44849233 | 0.44849233 | 0.00e+00 |
| Annualized return | 0.67989710 | 0.67989710 | 0.00e+00 |
| Max drawdown | 0.09834732 | 0.09834732 | 0.00e+00 |
| Drawdown amount | 119,475.72569250 | 119,475.72569250 | 0.00e+00 |
| Total commission | 3,612.75016050 | 3,612.75016050 | 0.00e+00 |
| Win rate | 1.00000000 | 1.00000000 | 0.00e+00 |

**All seven at `0.00e+00`** — not "within tolerance," bit-identical.
Gate script: [`parity_gate.py`](parity_gate.py), output:
[`results/parity.json`](results/parity.json). It runs in CI on every push, on both
macOS/clang and Linux/gcc.

<details>
<summary>Two known convention differences (on the record, not swept under the rug)</summary>

- **Annualized volatility** differs by `3.32e-04`:
  pandas' `.std()` defaults to `ddof=1` (sample), the C++ side uses `ddof=0` (population).
  The ratio is exactly `sqrt(n/(n-1))`.
- **Sharpe ratio** differs by `1.2594`: both are
  standard algorithms taking different annualization paths —
  C++ uses "mean daily excess return × √252", Python uses
  "(geometric annualized return − rf) / annualized volatility".
  The parent project's 2026-07-15 retirement note recorded "Sharpe differs by 0.018"; on this
  fixture the measured difference is `1.2594`.
  The two annualization paths diverge more as return skew grows, so that note was presumably
  taken on a different dataset — **the old record was not taken on faith; the measurement wins.**
- **Trade count**: Python counts fills, C++ counts round-trips, roughly 2:1 on the same set of
  trades.

</details>

## Round one: the hypothesis was the language — then it was falsified

**Hypothesis H1**: C++ is compiled and Python is interpreted, therefore C++ is faster. The gap
should be broadly consistent across sizes and strategies.

Four strategies present on both sides × five data sizes, fed **byte-identical** synthetic
market data. The table below is C++ in-process vs the pure Python engine (timings use `min`,
reasoning in [methodology](#what-was-done-to-make-these-numbers-trustworthy)):

| Strategy | 250 bars | 1,000 bars | 2,500 bars | 10,000 bars | 25,000 bars |
|---|---|---|---|---|---|
| `MA_CROSS` | 318.3× | 293.1× | 267.5× | 256.1× | 241.6× |
| `MACD` | 72.0× | 21.7× ⚠ | 8.7× | 2.0× | 0.9× ⚠ |
| `RSI` | 88.2× | 28.4× | 11.4× | 2.6× | 1.1× |
| `KDJ` | 97.2× | 32.8× | 13.6× | 3.4× | 1.4× |

If H1 held, every row would be a roughly horizontal line.

**It isn't.**

`MA_CROSS` does hold steady at 242–318× — consistent with the hypothesis. But the other three
**collapse sharply with scale**: at 25,000 bars `MACD` is only
**0.9×** — meaning **C++ lost to Python**.

Same language, same engine, same data. Change nothing but the strategy and the conclusion
reverses. **H1 cannot explain that. Falsified.**

## Round two: seven hypotheses, one at a time

### H2 · Algorithmic complexity order ✅ confirmed, and it is the primary cause

If the gap comes from complexity order, then regressing time against size in log-log space
gives the order directly: `t ∝ N^k` → `log t = k·log N + c`.

| Engine | Strategy | Fitted slope k | Verdict |
|---|---|---|---|
| C++ | `KDJ (engine now)` | **1.072** | **O(N)** linear |
| C++ | `MACD (incremental prototype)` | **1.062** | **O(N)** linear |
| C++ | `MACD (engine now)` | **1.054** | **O(N)** linear |
| C++ | `MACD (before the fix, O(N²))` | **1.970** | **O(N²)** quadratic |
| C++ | `MA_CROSS` | **1.066** | **O(N)** linear |
| C++ | `RSI (engine now)` | **1.052** | **O(N)** linear |
| Python | `KDJ` | **0.999** | **O(N)** linear |
| Python | `MACD` | **1.007** | **O(N)** linear |
| Python | `MA_CROSS` | **1.001** | **O(N)** linear |
| Python | `RSI` | **0.995** | **O(N)** linear |

**Python is k ≈ 1.00 across the board; C++'s MACD, *as it was before the fix*, is k ≈ 1.97 — quadratic.**

> The C++ rows are labelled "before the fix / incremental prototype / engine now". When this
> investigation was written, `MACD` / `RSI` / `KDJ` were all k ≈ 1.95; those three are now
> incremental in the engine and their slopes have dropped to k ≈ 1.06 (see
> [Round three](#round-three-fixed-then-re-measured)), which is why the "engine now" rows are
> linear. **The "before the fix" row is measured live from the original implementation frozen
> into the benchmark**, not copied from an old record — otherwise the conclusion would not be
> reproducible.

Open the source and the reason is immediate — the indicator helpers on `StrategyContext`
([`strategy_context.h`](../backtest_engine/include/backtest/strategy_context.h))
**recompute the entire series from bar 0 on every bar**:

- `macd()` rebuilds four length-N `std::vector`s per bar and reruns three full EMA recurrences
- `rsi()` rebuilds the difference array per bar and reruns Wilder smoothing from scratch
- `kdj()` reruns the whole K/D recurrence from bar n−1 every bar
- only `sma()` is O(period), which is why `MA_CROSS` escaped

The Python side's indicators are computed once, vectorized by numpy, in **O(N)**.

#### The decisive experiment: make it incremental and see what happens

Correlation is not enough. So an **incremental MACD** was written
(`IncrementalMACDStrategy` in [`bench_backtest.cpp`](bench_backtest.cpp)): the recurrence,
the coefficients and the seeding are copied line for line from the original; the only change
is that the EMA state is carried forward, making each bar O(1) with zero heap allocation.
**It must produce bit-identical results**, or the experiment is void.

| Bars | Original O(N²) | Incremental O(N) | Speedup | Result check |
|---|---|---|---|---|
| 250 | 0.175 | 0.044 | **4.0×** | ✅ bit-identical |
| 1,000 | 2.270 | 0.179 | **12.7×** | ✅ bit-identical |
| 2,500 | 14.533 | 0.495 | **29.4×** | ✅ bit-identical |
| 10,000 | 239.307 | 2.051 | **116.7×** | ✅ bit-identical |
| 25,000 | 1,444.018 | 5.866 | **246.2×** | ✅ bit-identical |

The speedup grows **monotonically** with size — that is the fingerprint of O(N²)→O(N).

And the most important line is hidden inside the numbers: at 25,000 bars the incremental MACD
takes 5.866 ms while `MA_CROSS` takes 5.899 ms —
**essentially the same**. Fix the algorithm and MACD immediately returns to `MA_CROSS`'s
magnitude; its ratio against Python goes from **0.9× (losing)
to 245× (winning)**, in line with `MA_CROSS`'s
242×.

> **Conclusion**: "the C++ MACD backtest loses to Python" has nothing to do with the language.
> It was a piece of C++ written as O(N²) losing to a piece of Python written as O(N).

Raw data: [`results/experiment_incremental.json`](results/experiment_incremental.json)

### H3 · Vectorization ✅ confirmed

Python's indicators are not computed by Python — they are computed by numpy: a C loop with
SIMD, sweeping a whole column at once.

Computing the same MACD over 25,000 bars:

| Approach | Time |
|---|---|
| Python + numpy, whole column at once | **0.560 ms** |
| C++ hand-written scalar loop, recomputed per bar | **≈ 1,657.756 ms** |

(The C++ figure is "full MACD run 1,663.655 ms − the near-indicator-free MA_CROSS run
5.899 ms", an approximation of the indicator portion.)

A ratio of about **2,963×**.

**But read that number carefully — it is not "numpy beats C++."** numpy *is* C underneath.
What is being compared above is "O(N) computed once" against "O(N²) recomputed per bar," and
the overwhelming majority of that 2,963× is complexity order, not
vectorization.

Swap in **well-written C++** and the conclusion changes immediately: the incremental version
from H2 runs the entire backtest in 5.866 ms, and within it the
indicator work (four floating-point operations per bar) is essentially free — that is,
**correctly implemented C++ does not lose to numpy on indicator computation, and is faster.**

So the part of H3 that holds is this, and it is valuable enough:

> Vectorization brings Python **to within the same order of magnitude as C** for bulk numeric
> work — a full MACD over 25,000 bars in 0.560 ms. It will not beat well-written
> C++, but it demolishes the premise that "using Python necessarily means being slow."

For a sense of scale: Python's indicator preparation is only
**0.04%** of its end-to-end time — almost
free. **Nearly all of Python's time goes into the per-bar loop**, which is its real weakness,
and exactly what H5 examines.

### H4 · Heap allocation ⚠️ contributes, but only as a constant factor

The incremental experiment changed two things at once: no more recomputation, and no more
per-bar allocation. Those need separating.

So a third version, `MACD_NOALLOC`: **still recomputes the whole series every bar** (still
O(N²)), but reuses one block of memory for its four buffers, allocating nothing in steady state.

| Bars | Original<br>O(N²)+alloc | No-alloc<br>O(N²) | Incremental<br>O(N) | Alloc<br>share | Algorithm<br>share |
|---|---|---|---|---|---|
| 250 | 0.175 | 0.117 | 0.044 | 44% | 56% |
| 1,000 | 2.270 | 1.431 | 0.179 | 40% | 60% |
| 2,500 | 14.533 | 8.370 | 0.495 | 44% | 56% |
| 10,000 | 239.307 | 132.333 | 2.051 | 45% | 55% |
| 25,000 | 1,444.018 | 826.510 | 5.866 | 43% | 57% |

All three versions produce **identical results**. Allocation accounts for roughly
**43%** of the available headroom, the algorithm for
**57%**.

But there is a more important observation: eliminating allocation buys only
**1.7×**, and the no-alloc version **is still quadratic** (slope k ≈
2.00 over the last two sizes).

> **Allocation optimization buys a constant factor; algorithmic optimization buys an order.**
> At scale, constant factors stop being worth much.

Raw data: [`results/experiment_allocation.json`](results/experiment_allocation.json)

### H5 · Data structures ✅ confirmed, and it overturns the fix

So where is Python's per-bar loop actually slow? Is it "the interpreter is slow"?

Measuring the specific operations inside each bar, against the same operations on numpy arrays:

| Operation | pandas DataFrame | numpy array | Ratio |
|---|---|---|---|
| `df.iloc[i]['close']` scalar lookup | 6.774 µs | 0.022 µs | **314×** |
| `df.iloc[:i+1]` history slice | 4.917 µs | 0.043 µs | **115×** |
| `df['ma5'].iloc[-1]` indicator read | 1.360 µs | 0.022 µs | **62×** |

The Python engine measures **39.6 µs per bar**, of which
**24.0 µs (61%)** goes purely into
DataFrame scalar lookups and slicing.

A DataFrame is designed for **whole-column batch operations**: every `df.iloc[i]['close']`
goes through index resolution, type dispatch and return-object construction. Element-wise
scalar access is its worst possible use.

> **Of the claim "Python is slow," 61% is not a Python problem at all —
> it is the wrong data structure.** Replacing the DataFrame with numpy arrays (without changing
> the semantics of a single line of Python) should bring per-bar cost from
> 39.6 µs down to about
> 15.6 µs — roughly
> 2.5× faster.

What remains after that is genuine interpreter overhead — and that part can only be addressed
by changing language.

> ⚠️ This experiment ran in a **different environment** from the main benchmark table:
> Python 3.13.11 / pandas 2.3.3 /
> numpy 2.3.5 (the main table used 3.10.19 /
> pandas 2.1.4). The absolute microsecond figures therefore cannot be added to the
> main table's — but what matters here is the **share**, and the share is insensitive to
> version. The environment is recorded in the result file's own `environment` block rather
> than left to guesswork.

Raw data: [`results/experiment_pandas_overhead.json`](results/experiment_pandas_overhead.json),
produced by [`exp_pandas_overhead.py`](exp_pandas_overhead.py)

### H6 · Transport layer ✅ confirmed, but only fatal for small jobs

The C++ engine is exposed as an HTTP service. How much does transport eat (25,000 bars)?

| Strategy | Full HTTP | In-process | Transport share |
|---|---|---|---|
| `MA_CROSS` | 63.921 | 5.899 | 90.8% |
| `MACD` | 1,714.445 | 1,663.655 | 3.0% |
| `RSI` | 1,153.329 | 1,085.608 | 5.9% |
| `KDJ` | 1,065.574 | 999.958 | 6.2% |

For a job like `MA_CROSS` where the engine itself needs only 5.899 ms,
**91% of the time goes into JSON serialization and the HTTP
round trip** — make the engine ten times faster and the user will not notice. For jobs where
the engine itself takes one or two seconds, transport falls to 3–6%.

> Optimize where the bottleneck is. The smaller the job, the more the transport layer *is* the
> bottleneck.

### H7 · Logging I/O ❌ falsified

The original hypothesis: the Python engine writes a log line inside its per-bar loop, and that
slows it down.

**Reading the source showed the premise itself was wrong** — the `logger.info` at
`engine.py:113` sits inside `for order in pending:`, so it fires **per fill**, not per bar.
Over 25,000 bars there are only about a thousand fills.

Measurement agreed: logging on 1470.6 ms vs logging off
1510.3 ms — a ratio of 0.97×, i.e. logging
"made it faster." That is obviously noise; the real difference is **below measurement
resolution**.

The benchmarks still run with logging off (which is the right thing to do), but **this factor
contributes nothing to the conclusion.** A hypothesis you raised and then falsified yourself
still gets written down — if only the confirmed hypotheses are reported, the reader has no way
to tell whether you cherry-picked.

### H8 · Cold start ⚠️ doesn't affect the engine, but does affect perceived speed

`import pandas` takes **386 ms**.

This is excluded from the engine timings (it is not the engine's cost), but for a usage pattern
like "run one small backtest," it costs more than the backtest itself. In a long-lived process
it is a one-time cost; in a command-line tool you pay it every time.

## Supplement: does changing Python version change the conclusion?

All the Python numbers above ran on **3.10.19** (the parent project's conda
environment). But CPython had a significant optimization pass starting in 3.11, and reporting
only one version is unfair to Python. So the entire Python side was rerun on this machine's
**3.13.11** (pandas 2.3.3 / numpy 2.3.5) — the C++ side
unchanged, same data, same strategies, same sampling.

At 25,000 bars:

| Strategy | Python 3.10.19 | Python 3.13.11 | Newer is faster by | C++ lead changes |
|---|---|---|---|---|
| `MA_CROSS` | 1,425.039 | 1,039.113 | **1.37×** | 241.6× → **176.2×** |
| `MACD` | 1,434.647 | 1,025.112 | **1.40×** | 0.9× → **0.6×** |
| `RSI` | 1,151.085 | 829.657 | **1.39×** | 1.1× → **0.8×** |
| `KDJ` | 1,378.555 | 1,010.517 | **1.36×** | 1.4× → **1.0×** |

**Python 3.13.11 is about 1.37× faster**, and that speedup cuts two ways:

- it **weakens** the "language" factor: on `MA_CROSS`, C++'s lead drops from
  242× to **176×**
- it **strengthens** the core conclusion: on `MACD`, C++ goes from
  0.9× to **0.62×** — **losing by more**

On 3.13.11, C++ **loses or ties on three of the four strategies** — `MACD`
0.62×, `RSI`
0.76×,
`KDJ`
1.01× —
holding its lead only on `MA_CROSS`.

> Worth noting: the "language/runtime" factor itself moves by **37%** just
> from a Python point release. The 246× from O(N²)→O(N) is structural
> and does not drift with the environment.
> **That is itself further evidence for "don't treat language as the primary variable."**

Raw data: [`results/backtest_py313.json`](results/backtest_py313.json)

## Attribution summary

Ordered by impact on final runtime:

| # | Factor | Magnitude | Nature | Fixable |
|---|---|---|---|---|
| 1 | **Algorithmic order** O(N²)→O(N) | up to **246×**, grows with N | complexity order | ✅ yes, biggest win |
| 2 | **Language / runtime** | **176–242×** (range from Python version) | constant factor | ⚠️ requires changing language |
| 3 | **Data structure** (pandas scalar indexing) | about **2.5×** | constant factor | ✅ switch to numpy arrays |
| 4 | **Heap allocation** | **1.7×** | constant factor | ✅ buffer reuse |
| 5 | **Transport layer** | **91%** of small jobs | fixed overhead | ✅ batch / in-process calls |
| 6 | **Cold start** | **386 ms** once | fixed overhead | ⚠️ amortized by a long-lived process |
| 7 | **Logging I/O** | below measurement resolution | — | nothing to fix |

**The most important line is the comparison between rows 1 and 2:**

In this dataset, **the gap from algorithmic order (up to 246×) is larger
than the gap from language choice (176–242×)**,
and the former grows without bound in N and does not drift with the environment, while the
latter is a bounded constant that moves 37% on a Python point release.

So "should this be C++ or Python" is mostly the wrong question. The question to ask is:
**can this computation be done once instead of recomputed at every step.**

## So when should you use which

### Where C++ clearly wins

**1. Inherently serial loops with cross-bar state that cannot be vectorized** — measured 242–318×

Per-bar decisions are a dependency chain: this bar's signal depends on the previous bar's
moving-average relationship, whether to trade depends on the current position, and the
position came from earlier fills. **No step can be batched ahead of time**, and numpy cannot
help. Python has to walk bar by bar, paying interpreter and object overhead each time. This is
C++'s home ground.

**2. Single operations near the language's overhead floor** — order book matching at
626 ns/order

In Python, one function call plus a few object constructions already costs hundreds of
nanoseconds. When an operation is tiny and performed enormously often, language overhead
dominates.

**3. When predictable tail latency is required** — order book p99.9 =
2,000 ns

No GC pauses. Python's garbage collector intervenes at unpredictable moments, which is fatal
for a matching engine.

**4. Small jobs invoked at high frequency** — parameter grid search

A 250-bar backtest: C++ 0.04 ms
vs Python 14 ms. Over a thousand
parameter sets that is the difference between interactive tuning and going to make coffee.

### Where Python clearly wins

**1. Bulk computation that a vectorized library can take** — the cost of using Python ≈ 0

A full MACD over 25,000 bars takes numpy only **0.560 ms**, which is
0.04% of the whole backtest.

⚠️ Note the wording: "cost ≈ 0," not "faster." Per H3's conclusion, **vectorization does not
beat well-written C++** — the incremental C++ version's indicator work is faster still. What it
beats is **badly written C++** — the O(N²) version measured here, by about
2,963×.

The real value is this: for this class of computation, choosing Python costs **almost nothing
in performance**, so the budget can go to development speed and readability instead. That is a
different claim from "Python is faster."

**2. Someone in the ecosystem already wrote the hard part in C**

Using Python does not mean running at Python speed. What matters is whether the hot path lands
in the interpreter or in a library. 61% of this Python engine's time went
into pandas scalar indexing (H5) — the classic symptom of a hot path falling back into the
interpreter and object layer. Same library, and using it right versus wrong differs by
314×.

**3. Cost to write and change** — 1,431 lines vs 8,570 lines

What the Python reference engine does in 1,431 lines, the C++ engine takes 8,570
lines to do (the latter does more — risk management, market rules, portfolio backtesting and
six additional strategies — so this comparison is a rough order-of-magnitude reference, not a
like-for-like line count).

### The one-line decision rule

> **Can the hot path be vectorized?**
> Yes → Python + numpy; the marginal benefit of writing C++ is small, and as measured here it
> may even be slower.
> No (serial state dependency) → C++ has a two-order-of-magnitude advantage and is worth it.

A backtest engine is **both**: indicator computation vectorizes, per-bar execution decisions do
not. So the optimum is not a binary choice but a **hybrid** — vectorized precomputation for
indicators, C++ for the serial loop.

That happens to be exactly the architecture the Python reference engine had (reading
pre-computed indicator columns), and exactly the direction the current C++ engine should move in.

## An example that must not be compared — since diagnosed and fixed

`KDJ` appears in the tables above, but **its numbers must not be read as a speed comparison.**

> ✅ **This defect has been fixed** (`kdj_strategy.cpp`). The table and analysis below are the
> **pre-fix** state, kept verbatim because they are the most valuable methodological lesson of
> the investigation. Post-fix measurements are at the end of this section.

| Bars | C++ fills | Python fills |
|---|---|---|
| 250 | 41 | 0 |
| 1,000 | 160 | 3 |
| 2,500 | 392 | 3 |
| 10,000 | 1,674 | 13 |
| 25,000 | 4,149 | 21 |

Up to **two orders of magnitude** apart. The cause is in the strategy logic itself:

| | Buy filter | Sell filter |
|---|---|---|
| **C++** | `k < overbought_` → **k < 80** | `k > oversold_` → **k > 20** |
| **Python** | `k < oversold` → **k < 20** | `k > overbought` → **k > 80** |

The C++ comment says "K crosses above D, **in the low zone (oversold)**," but the code tests
`< overbought_` (80) — a condition that is almost always true, so **the oversold filter never
takes effect.** On the Python side, comment and code agree.

The two implementations are not running the same strategy. In that situation "C++ is 1.4×
faster than Python" is a **meaningless number** — their workloads differ by two orders of
magnitude.

> This is kept here because it is the most valuable methodological lesson of the whole
> investigation: **before timing anything, prove that both sides are doing the same thing.**
> This repository's benchmark therefore has a built-in workload check (comparing fill counts and
> final equity), flagging mismatches — otherwise it is very easy to compare two different
> things all the way to a beautiful conclusion.

### Measured after the fix

With the two C++ thresholds corrected (now consistent with `description()`, the parameter
schema, the README, and the Python reference implementation), the workloads on the same
synthetic data **align exactly**:

| Bars | C++ fills (before) | C++ fills (after) | Python fills |
|---|---|---|---|
| 1,000 | 160 | **3** | 3 |
| 2,500 | 392 | **3** | 3 |
| 10,000 | 1,674 | **13** | 13 |

They used to differ by 53–131×; now they match one for one. That also confirms the attribution
was right: the divergence really did come from those two swapped thresholds and nothing else.

⚠️ The fill-count table at the start of this section is still pre-fix data —
`results/backtest.json` is the output of a run that predates the fix, and rerunning the full
benchmark would also move every Python-side number (this machine's pandas version differs from
the recorded one), so it is left for the next complete re-measurement. The fix itself is guarded
by five cases in `tests/test_kdj_strategy.cpp`, three of which were **verified to go red while
the defect was present**.

**Cancel** — a problem found, then fixed

Originally this was a full-book linear scan:
[`cancel_order`](../orderbook_simulator/src/limit_order_book.cpp) walked every bid level,
scanned each level's entire FIFO queue, then did the same for asks. No `order_id` index.
Cancelling a non-existent id was always the worst case — both sides scanned in full.

| Metric | Before index | After index | Change |
|---|---|---|---|
| **Amortized** | 44,389 ns | **142 ns** | **312×** |
| p50 | 42,208 ns | 84 ns ⚠️ | 502× |
| p99 | 97,958 ns | 334 ns ⚠️ | —— |
| p99.9 | 126,333 ns | 792 ns ⚠️ | —— |
| Cancel/submit p50 | 48.2× | 0.13× | —— |

**Why the headline uses the amortized value and not p50.** After the fix, a cancel is down to
2.0 clock ticks (measured `steady_clock` granularity on
this machine: 41 ns), so a single measurement carries roughly
±24% quantization error — the trailing
digits on the ⚠️ rows are artifacts, not signal. Before the fix, p50 had
1,029 ticks and was entirely trustworthy; after, it
is not.

So the defensible multiple is the amortized
**312×**, not the
502× that p50 implies. The
latter looks better, but part of it comes from *the thing under test becoming too fast to
measure*, and treating that as a result would be self-deception.

Both datasets were produced by the **same** benchmark binary (both with warmup, both measuring
clock granularity); the "before" row comes from running today's `bench_orderbook.cpp` against
the pre-fix commit. A before/after across different harnesses is not a comparison, and that
matters more than being able to quote a bigger number.

**Done at the same time, with an unexpected payoff.** `PriceLevel`'s `is_empty()` /
`order_count()` / `total_quantity()` were all O(n) — because cancellation is soft (it sets
`is_active = false` without dequeuing), each had to scan past the "corpses" in the queue.
After switching to two incrementally maintained counters:

| Metric | Before index | After index |
|---|---|---|
| `get_depth(10)` p50 @ 1,000 orders | 250 ns | 126 ns |
| `get_depth(10)` p50 @ 10,000 orders | 250 ns | 84 ns |
| `get_depth(10)` p50 @ 100,000 orders | 583 ns | 125 ns |
| Submit p50 | 875 ns | 626 ns |

Note those three `get_depth` rows: before the change it grew with book depth from
250 to 583 ns;
after, it is **essentially flat**. That is the substance of this change — not a smaller
constant, a changed order.

**Submit got faster too**, despite now performing an extra index insertion. The reason is that
every submit calls `cleanup()`, which calls `is_empty()` on every level; going from O(n) to
O(1) there saves more than the index insertion costs.

Behavioral equivalence is guarded by the randomized differential test in
[`test_differential.cpp`](../orderbook_simulator/tests/test_differential.cpp): 200 seeds × 300
steps = 60,000 operations, fill-for-fill identical to a reference model. Guardrail first, then
performance — that order is not negotiable.

### Timings use `min`, not the median

Benchmark interference is **one-directional** — background activity can only make a program
slower, never faster. So `min` is the best estimator of "true cost," whereas the median gets
lifted wholesale by system noise.

This is not theoretical fastidiousness: in one run, `KDJ` at the largest size reached a
`max/min` of **5.52×**, its median inflated by 46%, and it produced a **−68.6% "negative
transport overhead"** — an impossible number.

Median, p95 and max are still written to the results files in full, and used to judge whether
each cell is clean. Cells with `max/min > 1.5` are flagged ⚠ in the tables.

### The two benchmarks must run serially

On the first attempt, the order book and backtest benchmarks were backgrounded in parallel.
**They competed for CPU and both datasets were void.** They are now chained with `&&`.

### Workload verification

Comparing speed presupposes that both sides are doing the same work. Every cell compares
**fill count** (primary criterion) and **relative error of final equity** (secondary), flagging
mismatches and listing them at the end of the output.

Fill count is the primary criterion rather than equity because equity is the compounded result
of N trades — any tiny difference is amplified — whereas "how many trades were made" is what
actually determines how much work the engine did.

### Clock resolution

`steady_clock` on this machine has a measured minimum non-zero interval of
**41 ns**. Some order book operations are now only 2–3 ticks, so
the benchmark measures the granularity at runtime (it is not hardcoded — CI runs on both macOS
and Linux, where it differs by orders of magnitude) and marks which of its own percentiles are
quantization-limited, recording the relative error alongside.

Each order book case therefore reports two numbers: per-operation **percentiles** (which show
the tail, but are quantized) and **amortized** total-time-over-count (immune to quantization,
but blind to the tail). Both are needed for a complete picture.

### Synthetic data design

The scale curve needs 25,000 bars while the real fixture has only 180, so scale testing uses
synthetic market data. The generator is a hand-rolled linear congruential PRNG (not dependent
on the `random` module's implementation details), so the same seed produces an identical
sequence on any machine and any Python version. **Both engines are fed the same JSON file.**

Prices follow a **mean-reverting** process rather than a random walk with drift, and that was
changed after being bitten: the first version had 0.0002/day of drift, which looked fine at 250
bars, but compounded over 25,000 bars sent prices into the tens of thousands and account equity
to ~1e17 — a range that trips the C++ `lot_floor` clamp at 2e9 shares
([`strategy_context.h:80`](../backtest_engine/include/backtest/strategy_context.h)) while
Python has no clamp, so the workload check **reported a false failure**. The sine cycle's
amplitude (0.0015) was likewise tuned empirically to keep equity between 1× and 2.2× of initial
capital at any size. The reasoning is recorded in [`benchlib.py`](benchlib.py)'s comments.

### Deliberate fairness trade-offs

- **Python computes only the indicator columns the strategy actually needs.** The parent
  project's `add_indicators()` entry point computes the trend + momentum + volatility + volume
  families in one pass; using that as Python's indicator cost would saddle it with a pile of
  work it never uses.
- **C++ reports the same number under "pure engine" and "end-to-end"** — it has no separate
  indicator preparation phase; indicators are computed inside `on_bar`. So comparing C++
  against Python's pure-engine figure is actually **unfavorable to C++** (its loop is still
  carrying the indicator computation). Both framings are reported.
- **Timings exclude process startup and imports** (not the engine's cost), but cold start is
  recorded separately.

### Known limitations

- Single process, single thread — **concurrency is not measured.**
- The Python reference engine is frozen at its 2026-07-15 retirement state; the C++ engine has
  since grown risk management, market rules, portfolio backtesting and more.
  **The comparison is made only on the feature surface both share.**
- `MACD` at the largest size is flagged noisy (`max/min > 1.5`); read that cell as a trend, not
  a precise value.
- The C++ indicator cost in H3 is **estimated by subtracting two strategies**, not measured
  directly. It is an approximation.

## Round three: fixed, then re-measured

The first two rounds identified the cause. This round fixes it and measures again.

`macd()` / `rsi()` / `kdj()` in `strategy_context.h` are now incremental recurrences: the
carriers persist, and each bar advances one step. The state lives on **each symbol's**
`SymbolState` — it cannot live on the strategy object, because a portfolio backtest shares one
strategy instance across all symbols, and it cannot live on `StrategyContext`, which is rebuilt
on the stack every bar.

### The control arm is frozen, not remembered

Fixing this creates an immediate problem: once the engine's `MACD` is fast, `MACD` vs
`MACD_INCREMENTAL` compares two identical things and the experiment can never be reproduced
again.

So the pre-fix O(N²) implementation was **frozen verbatim** into
[`bench_backtest.cpp`](bench_backtest.cpp) as the `MACD_NAIVE` arm. The "before" column below is
that arm **measured now**, not copied from an old record.

| Bars | Before, O(N²) | Engine now, O(N) | Speedup | Economics |
|---|---|---|---|---|
| 250 | 0.175 | 0.045 | **4×** | ✅ bit-identical |
| 1,000 | 2.270 | 0.183 | **12×** | ✅ bit-identical |
| 2,500 | 14.741 | 0.470 | **31×** | ✅ bit-identical |
| 10,000 | 238.390 | 2.085 | **114×** | ✅ bit-identical |
| 25,000 | 1,441.031 | 5.738 | **251×** | ✅ bit-identical |

The speedup grows **monotonically** (4× → 251×) —
the fingerprint of O(N²)→O(N), matching the shape round two measured with a prototype.

**The "Economics" column is the precondition for the whole table.** Every cell compares trade
count and final equity: the two arms must be bit-identical, or they are not running the same
strategy and the speedup means nothing. If any cell were ❌, the generator exits non-zero.

### The most convincing line: four strategies converge

At 25,000 bars, the four strategies now cost:

| Strategy | Time |
|---|---|
| `MA_CROSS` (unchanged, the control) | 5.541 ms |
| `MACD` | 5.738 ms |
| `RSI` | 5.550 ms |
| `KDJ` | 5.816 ms |

In round one `MACD` was two orders of magnitude slower than `MA_CROSS`; now they are
essentially the same. `MA_CROSS` was not modified and its timing did not move — it is the fixed
point of this comparison.

That closes out round one's anomaly completely: `MACD` lost to Python because of how those three
indicators were *implemented*, not because of the language.

### How bit-exactness is actually guaranteed

Not by "the numbers came out close." By three layers:

1. **A golden fixture** (`backtest_engine/tests/data/indicator_golden.json`) captured from the
   naive implementations **before** the rewrite, recording every indicator on every bar as the
   double's **bit pattern**, not a decimal. After the rewrite the same fixture must be hit
   bit-for-bit — by **both** the full-recompute path and the incremental path.
2. **`-ffp-contract=off`**: the compiler may not contract `a*b+c` into an FMA. Measured, the
   same source otherwise emits 3 `fmadd` instructions, and an FMA rounds once instead of twice —
   a 1 ULP difference. Without this, the two paths could get different contraction decisions and
   bit-exactness would be meaningless.
3. **The parity gate**: all seven economic metrics against the Python reference are still
   `0.00e+00`.
